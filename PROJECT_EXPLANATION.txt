SIMPLE BANK SYSTEM (Django) - FULL PROJECT EXPLANATION

Generated by reading every file in the project. This document explains what

--------------------------------------------------------------------------------
1. OVERALL ARCHITECTURE
--------------------------------------------------------------------------------
Django splits an app into a PROJECT (global config) and one or more APPS
(features). This repo has:

  bankproject/   -> the project: global settings, root URL routing, server
                    entry points (WSGI/ASGI)
  bank/          -> the one app: all banking logic (models, forms, views,
                    urls, admin, templates)

Request flow for any page:
  browser request
    -> bankproject/urls.py   (root URL table)
    -> bank/urls.py          (app URL table)
    -> a view function in bank/views.py
    -> reads/writes bank/models.py (Account, Transaction tables)
    -> renders an HTML template from bank/templates/bank/
    -> response sent back to browser

Data model (2 database tables):
  Account     - one per User (OneToOneField). Holds account_number,
                account_type, balance.
  Transaction - many per Account (ForeignKey). An append-only ledger: every
                deposit/withdraw/transfer creates a row here.

2. TOP-LEVEL FILES
--------------------------------------------------------------------------------

manage.py
---------
Django's command-line utility. Every command you run (runserver, migrate,
createsuperuser, etc.) goes through this file.
  - Sets the environment variable DJANGO_SETTINGS_MODULE to
    'bankproject.settings' so Django knows which settings file to load.
  - Imports execute_from_command_line from Django and forwards sys.argv
    (whatever you typed after "python manage.py") to it.
  - If Django isn't installed, raises a helpful ImportError reminding you to
    activate your virtualenv.
This file is 100% Django boilerplate - nobody customizes it.

requirements.txt
----------------
Lists the one dependency: Django>=5.0,<6.1. Installed via
`pip install -r requirements.txt`.

README.md
---------
Human-readable project overview: what the app does, folder structure, how to
run it, a plain-English description of the data model, and a set of
interview-style Q&A explaining design decisions (why atomic transactions, why
Django's built-in User model, what you'd add for production).

db.sqlite3
----------
The actual SQLite database file. Created the first time you run
`python manage.py migrate`. Contains the real Account/Transaction/User rows
for whatever data you've created while testing the app locally.

venv/ and .venv/

Two Python virtual environments (folders full of an isolated Python
interpreter + installed packages, e.g. Django itself). Not part of your
actual code - purely local tooling so `pip install` doesn't affect your

3. PROJECT-LEVEL CONFIG: bankproject/
--------------------------------------------------------------------------------

bankproject/__init__.py
------------------------
Empty file. Its only job is to make the `bankproject` folder importable as a
Python package (so `import bankproject.settings` works).

bankproject/settings.py
------------------------
The single global configuration file for the whole Django project.

  BASE_DIR
    Path(__file__).resolve().parent.parent
    -> computes the project root folder so other paths (like the sqlite file)
       can be built relative to it, regardless of where you run the command
       from.

  SECRET_KEY
    A random string Django uses for cryptographic signing (sessions, CSRF
    tokens, password reset tokens). The one committed here is a Django
    "insecure" placeholder auto-generated by `startproject` - fine for local
    dev, but MUST be replaced with a secret, environment-provided value before
    any real deployment.

  DEBUG = True
    Turns on Django's detailed error pages (full tracebacks) and disables
    some production safety checks. Must be False in production - leaving it
    True publicly would leak source code and settings on any error.

  ALLOWED_HOSTS = ['localhost', '127.0.0.1']
    Security allowlist: Django refuses to serve requests whose Host header
    isn't in this list. Prevents HTTP Host header attacks.

  INSTALLED_APPS
    The list of Django "apps" that are active. Includes the standard set
    Django ships with:
      django.contrib.admin        -> the /admin/ site
      django.contrib.auth         -> User model, login/logout, permissions
      django.contrib.contenttypes -> generic relations support (used by auth)
      django.contrib.sessions     -> server-side session storage (login state)
      django.contrib.messages     -> the one-time "flash" messages framework
                                      (the green/red banners you see after
                                      an action)
      django.contrib.staticfiles  -> serves CSS/JS/image files in dev
      bank                        -> YOUR app, where all the banking logic
                                      lives

  LOGIN_URL = 'login'
  LOGIN_REDIRECT_URL = 'dashboard'
  LOGOUT_REDIRECT_URL = 'login'
    Tell Django's auth system (and your own @login_required decorator) where
    to send users: unauthenticated users trying to view a protected page get
    redirected to the 'login' URL name; after a successful login they land on
    'dashboard'; after logout they land back on 'login'.

  MIDDLEWARE
    An ordered pipeline every request/response passes through:
      SecurityMiddleware         -> adds security-related HTTP headers
      SessionMiddleware           -> attaches request.session (login state)
      CommonMiddleware            -> misc URL normalization
      CsrfViewMiddleware          -> enforces CSRF token checking on POSTs
                                      (this is why every <form> in the
                                      templates has {% csrf_token %})
      AuthenticationMiddleware    -> attaches request.user
      MessageMiddleware           -> attaches request "flash" messages
      XFrameOptionsMiddleware     -> blocks the site being embedded in an
                                      <iframe> (clickjacking protection)

  ROOT_URLCONF = 'bankproject.urls'
    Tells Django which file holds the top-level URL routing table.

  TEMPLATES
    Configures the Django template engine. APP_DIRS: True means Django
    automatically looks inside every installed app's templates/ folder
    (which is why bank/templates/bank/*.html is found automatically).
    context_processors add `request`, `user`, and `messages` automatically
    into every template's context, so templates can reference
    {{ user.username }} or loop over `messages` without the view passing
    them explicitly.

  WSGI_APPLICATION = 'bankproject.wsgi.application'
    Points to the WSGI entry point used when deploying with a real
    webserver.

  DATABASES
    Configured for SQLite, with the file living at BASE_DIR / 'db.sqlite3'.
    Zero-config, file-based - good for learning/demo, would be swapped for
    Postgres/MySQL in production.

  AUTH_PASSWORD_VALIDATORS
    Four built-in password strength checks Django runs when a user sets a
    password (via RegisterForm, since it wraps UserCreationForm):
      - UserAttributeSimilarityValidator -> rejects passwords too similar to
        your username/email
      - MinimumLengthValidator            -> rejects too-short passwords
      - CommonPasswordValidator            -> rejects passwords found in a
        list of the most common leaked passwords
      - NumericPasswordValidator            -> rejects all-digit passwords

  LANGUAGE_CODE / TIME_ZONE / USE_I18N / USE_TZ
    Internationalization/timezone defaults (US English, UTC, timezone-aware
    datetimes stored in the DB).

  STATIC_URL = 'static/'
    URL prefix under which static files (CSS/JS/images) are served.

bank/models.py  (THE DATA LAYER)
----------------------------------
Defines the two database tables. This is where the "shape" of the bank's
data lives.

  class Account(models.Model):
      user = models.OneToOneField(User, on_delete=models.CASCADE,
                                   related_name="account")
        -> Exactly one Account per Django User. related_name="account" is
           what makes `request.user.account` work everywhere in views.py.
           on_delete=CASCADE means if a User is deleted, their Account row
           is deleted too.

      account_number = models.CharField(max_length=12, unique=True,
                                         editable=False)
        -> A unique public-facing identifier people transfer money to.
           editable=False keeps it out of Django admin/forms by default -
           it's system-generated, not user-editable.

      account_type = models.CharField(..., choices=ACCOUNT_TYPE_CHOICES,
                                       default="SAVINGS")
        -> Either "SAVINGS" or "CURRENT" (a Django `choices` field: stores
           the short code in the DB, but get_account_type_display() in
           templates renders the human label "Savings"/"Current").

      balance = models.DecimalField(max_digits=12, decimal_places=2,
                                     default=0)
        -> The current balance. DecimalField (not FloatField!) is
           deliberately used because floating point numbers introduce
           rounding errors that are unacceptable for money.

      created_at = models.DateTimeField(auto_now_add=True)
        -> Automatically set once, at creation time.

      def save(self, *args, **kwargs):
          if not self.account_number:
              self.account_number = uuid.uuid4().int.__str__()[:10]
          super().save(*args, **kwargs)
        -> Overrides the default save() method. The FIRST time an Account is
           saved (account_number is still blank), it generates a "random
           enough" 10-digit numeric string from a UUID's integer
           representation and uses that as the account number. On every
           later save (e.g. updating the balance), account_number is already
           set, so this block is skipped and the number never changes.

      def __str__(self):
          return f"{self.user.username} - {self.account_number}"
        -> How an Account displays as text (e.g. in Django admin dropdowns).

  class Transaction(models.Model):
      account = models.ForeignKey(Account, on_delete=models.CASCADE,
                                   related_name="transactions")
        -> Many Transactions belong to one Account. related_name
           "transactions" is what makes `account.transactions.all()` work.

      transaction_type = models.CharField(..., choices=TRANSACTION_TYPES)
        -> One of DEPOSIT / WITHDRAW / TRANSFER_OUT / TRANSFER_IN.
           TRANSFER_OUT/IN exist (instead of a single "TRANSFER" type)
           because a transfer touches TWO accounts, and each account's ledger
           needs its own row describing what happened FROM THAT ACCOUNT'S
           point of view.

      amount = models.DecimalField(..., validators=[MinValueValidator(0.01)])
        -> Must be a positive amount (DB-level constraint, on top of the
           form-level validation in forms.py).

      balance_after = models.DecimalField(max_digits=12, decimal_places=2)
        -> A SNAPSHOT of what the account's balance was immediately after
           this transaction posted. This is the key design decision that
           makes the ledger self-auditing: even if you only had this table
           and the live `balance` field disappeared, you could always tell
           what the balance was at any point in time by reading the most
           recent Transaction. It also makes rendering the history page
           trivial - no need to recompute running totals.

      reference = models.CharField(max_length=40, blank=True, null=True)
        -> A shared ID written to BOTH rows created by a single transfer (the
           TRANSFER_OUT row on the sender's account and the TRANSFER_IN row
           on the receiver's account). Lets you later prove/trace "these two
           ledger entries on two different accounts are actually one logical
           event."

      note = models.CharField(max_length=255, blank=True, null=True)
        -> Optional free-text memo the user can attach (e.g. "rent",
           "birthday gift").

      timestamp = models.DateTimeField(auto_now_add=True)
        -> Set automatically when the row is created.

      class Meta:
          ordering = ["-timestamp"]
        -> Every query on Transaction is newest-first by default, unless
           overridden.

      def __str__(self):
          return f"{self.transaction_type} of {self.amount} on
                    {self.account.account_number}"
        -> Text representation, used in Django admin.

bank/forms.py  (SERVER-SIDE VALIDATION)
------------------------------------------
One Django Form class per user action. Forms validate incoming POST data
BEFORE it ever touches the database, and re-render with error messages if
something's invalid.

  class RegisterForm(UserCreationForm):
      account_type = forms.ChoiceField(choices=Account.ACCOUNT_TYPE_CHOICES)
      class Meta:
          model = User
          fields = ["username", "email", "password1", "password2",
                    "account_type"]
    -> Extends Django's OWN built-in UserCreationForm (which already
       validates username uniqueness, matches password1==password2, and
       runs AUTH_PASSWORD_VALIDATORS). One extra field, account_type, is
       bolted on so the user can choose Savings/Current at signup. Note this
       field isn't a User model field - it's just collected here and
       consumed manually in the view (see register_view below).

  class DepositForm(forms.Form):
      amount = forms.DecimalField(max_digits=12, decimal_places=2,
                                   min_value=0.01)
      note = forms.CharField(max_length=255, required=False)
    -> Just validates the amount is a positive decimal within range, and an
       optional note.

  class WithdrawForm(forms.Form):
      (identical shape to DepositForm)

  class TransferForm(forms.Form):
      to_account_number = forms.CharField(max_length=12,
                            label="Recipient account number")
      amount = forms.DecimalField(max_digits=12, decimal_places=2,

bank/views.py  (THE BUSINESS LOGIC)
--------------------------------------
One function per page/action. This is the heart of the app.

  register_view(request)
    - GET  -> shows a blank RegisterForm.
    - POST -> validates the form; if valid:
        1. form.save() creates the User row (UserCreationForm handles
           password hashing).
        2. Account.objects.create(user=user, account_type=...) immediately
           creates that user's one-and-only Account, so nobody can ever be a
           User without an Account.
        3. login(request, user) logs them straight in (no separate login
           step needed after registering).
        4. messages.success(...) queues a one-time flash message.
        5. redirect("dashboard") - Post/Redirect/Get pattern, avoids
           re-submitting the form if the user refreshes the page.

  @login_required
  dashboard_view(request)
    - account = request.user.account  (this only works because of
      related_name="account" on the OneToOneField in models.py)
    - recent_transactions = account.transactions.all()[:5]  (thanks to
      related_name="transactions" and the model's default -timestamp
      ordering, this is simply "the 5 newest transactions")
    - Renders dashboard.html with both.

  @login_required
  deposit_view(request)
    - GET  -> blank DepositForm
    - POST -> validate amount, then:
        with db_transaction.atomic():
            account.balance += amount
            account.save()
            Transaction.objects.create(account=account,
                transaction_type="DEPOSIT", amount=amount,
                balance_after=account.balance, note=...)
      db_transaction.atomic() wraps the balance update AND the ledger insert
      in a single database transaction. If the Transaction insert somehow
      failed after the balance was already changed, atomic() rolls BOTH
      operations back - the balance can never silently drift out of sync
      with the ledger. This is the single most important correctness
      pattern in the whole app, repeated in every money-moving view.
    - On success: flash message + redirect to dashboard.

  @login_required
  withdraw_view(request)
    - Same shape as deposit, but BEFORE touching the database it checks:
        if amount > account.balance:
            messages.error(request, "Insufficient balance.")
      This is a plain server-side comparison - critically, it happens in
      Python/the view, not just via HTML "min"/"max" attributes or
      JavaScript, so it can't be bypassed by a user editing the form in
      devtools or scripting a raw POST request.
    - If sufficient: same atomic() balance-decrement + Transaction("WITHDRAW")
      pattern as deposit.

  @login_required
  transfer_view(request)
    - GET  -> blank TransferForm
    - POST -> validate form, then:
        1. Look up to_account = Account.objects.get(account_number=to_number)
           - if it doesn't exist, catches Account.DoesNotExist and shows
             "Recipient account not found." (re-renders the same page
             instead of redirecting, so the entered amount/note aren't
             lost... actually note: it re-renders with the SAME form
             object, so validated values are preserved for correction).
        2. Guards:
             - to_account.pk == account.pk -> blocks transferring to
               yourself
             - amount > account.balance -> blocks overdrawing
        3. If both guards pass:
             reference = str(uuid.uuid4())[:8]
             with db_transaction.atomic():
                 # debit sender
                 account.balance -= amount
                 account.save()
                 Transaction.objects.create(account=account,
                     transaction_type="TRANSFER_OUT", amount=amount,
                     balance_after=account.balance, reference=reference, ...)
                 # credit receiver
                 to_account.balance += amount
                 to_account.save()
                 Transaction.objects.create(account=to_account,
                     transaction_type="TRANSFER_IN", amount=amount,
                     balance_after=to_account.balance,
                     reference=reference, ...)
           All FOUR writes (2 balance saves + 2 Transaction inserts) happen
           in one atomic block spanning TWO different Account rows. If any
           one write fails, all four roll back - money can never be
           deducted from the sender without being credited to the receiver
           (or vice versa). Both Transaction rows share the same
           `reference` UUID so they can be traced as one logical transfer
           even though they live on two unrelated accounts.
    - On success: flash message naming the recipient, redirect to dashboard.

  @login_required
  transaction_history_view(request)
    - account = request.user.account
    - transactions = account.transactions.all()   (ALL of them, unlike the
      dashboard's [:5] slice)
    - Renders transaction_history.html - the full ledger/audit trail.

  Note: every view except register_view is decorated @login_required,
  meaning an anonymous visitor hitting /deposit/, /withdraw/, /transfer/,
  /history/, or / (dashboard) gets redirected to LOGIN_URL ('login')
  automatically - this is enforced by Django itself, not custom code.

5. TEMPLATES: bank/templates/bank/

All pages extend one shared base template using Django's template

base.html
-----------
The shared page shell.
  - Inline <style> block: dark navy (#14213d) + orange (#fca311) color
    scheme, simple card-style container, styled table/inputs/buttons. No
    CSS framework - just hand-written CSS for a clean, minimal look.
  - <nav> bar:
      - Always shows a "Dashboard" link.
      - {% if user.is_authenticated %} shows Deposit/Withdraw/Transfer/
        History links plus "Hi, {{ user.username }}" and Logout.
      - else shows Login/Register links.
    (user.is_authenticated is available in every template automatically
    because of the auth context processor configured in settings.py.)
  - {% for message in messages %} loop: renders Django's flash messages
    (the ones queued via messages.success()/messages.error() in views.py)
    as green ("success") or red ("error") banners, then clears them.
  - {% block content %}{% endblock %} - the slot every child template fills
    in with its own page-specific content.

dashboard.html
----------------
  - Extends base.html, fills in the title and content blocks.
  - Shows a decorative SVG illustration via {% static %} (see note below -
    this image doesn't currently exist on disk).
  - Welcome heading, account number, account_type (rendered via
    {{ account.get_account_type_display }} - Django's auto-generated method
    for any `choices` field, turning "SAVINGS" into "Savings").
  - Large balance display: <p class="balance">${{ account.balance }}</p>.
  - "Recent Transactions" table, looping over recent_transactions (the
    5-item slice passed from dashboard_view), or "No transactions yet." if
    empty.
  - Link to the full history page.

login.html
------------
  - Standard {% csrf_token %} + {{ form.as_p }} + submit button pattern,
    handled by Django's built-in LoginView.
  - Link to the register page for new users.
  - NOTE: as currently written on disk, this file's entire content appears
    to be duplicated (the {% extends %}/{% block %} markup is repeated
    twice in the same file). Django does not allow {% extends %} or a
    same-named {% block %} to appear more than once in a single template,
    so this will raise a TemplateSyntaxError as soon as /login/ is
    rendered. This should be fixed by deleting the duplicated second half
    of the file.

register.html
---------------
  - Same csrf_token + form.as_p + submit pattern for RegisterForm.
  - Link back to login for existing users.

deposit.html / withdraw.html
--------------------------------
  - Nearly identical: show current balance, then a csrf_token + form.as_p +

transfer.html

6. KNOWN ISSUES / THINGS TO FIX
--------------------------------------------------------------------------------
1. login.html has its entire template content duplicated in one file,
   which will cause a TemplateSyntaxError ({% extends %} / {% block %}
   cannot repeat). Fix: remove the duplicated second half of the file.

2. dashboard.html and login.html reference static images
   (bank/images/dashboard-illustration.svg, bank/images/bank-illustration.svg)
   via {% static %}, but no `static/` directory exists anywhere under
   bank/. These images will simply 404 (broken image icon) - the rest of
   the page still renders fine.

3. No automated tests yet (bank/tests.py is an empty stub).

4. Concurrency: transfer_view/deposit_view/withdraw_view don't use
   select_for_update() to lock Account rows, so two simultaneous requests
   against the same account (e.g. two withdrawals in a race) could both
   read the same starting balance before either writes back, in rare cases
   letting a balance go negative. Fine for a learning project; would need
   fixing for real money.

5. SECRET_KEY is a hardcoded, publicly-visible placeholder and DEBUG=True.
   Both need to change (SECRET_KEY -> environment variable, DEBUG -> False)
   before any real deployment.

7. HOW THE PIECES FIT TOGETHER (END-TO-END EXAMPLE)
--------------------------------------------------------------------------------
"A logged-in user deposits $50."

  1. Browser GETs /deposit/ -> bank/urls.py routes to deposit_view.
  2. deposit_view (GET branch) renders deposit.html with a blank
     DepositForm.
  3. User fills in amount=50, clicks Deposit -> browser POSTs to /deposit/,
     including the CSRF token from {% csrf_token %}.
  4. CsrfViewMiddleware verifies the token; AuthenticationMiddleware has
     already attached request.user from the session cookie
     (SessionMiddleware); @login_required already confirmed the user is
     authenticated, or this request would never have reached the view.
  5. deposit_view (POST branch): DepositForm(request.POST) validates
     amount is a positive decimal.
  6. Inside db_transaction.atomic(): account.balance increases by 50 and
     is saved; a new Transaction row is created with
     transaction_type="DEPOSIT", amount=50, balance_after=<new balance>.
  7. messages.success(...) queues a flash message.
  8. redirect("dashboard") sends a 302 to /.
  9. Browser GETs / -> dashboard_view -> renders dashboard.html showing
     the updated balance, the new deposit at the top of
     recent_transactions, and the green success banner from base.html's
     messages loop.
